# servstart

Трей-сервис управления **локальными LLM-бэкендами и моделями** (ASUS ROG Flow Z13,
Strix Halo gfx1151). После запуска сам находит в системе доступные бэкенды и
модели, сопоставляет их по справочнику из сети и даёт запускать/останавливать
модели из каскадного меню в системном трее.

**Отдельный проект**, не связанный с `z13tray`/`z13ctl` (то управляет железом
ноутбука). Здесь — только инференс LLM.

## Структура

```
servstart/
├── servstart.py      главный апплет (GTK3 + AyatanaAppIndicator3) — трей, меню, окна
├── llm.py            вся логика без GTK (discovery, сопоставление, конфиг, запуск, метрики)
├── backends.json     info-файл: справочник бэкендов из сети (для сопоставления)
├── gen_icons.py      генератор иконок-«светофора» (чистый Python, без PIL/cairo)
├── icons/            servstart-gray/green/red.png (генерируются gen_icons.py)
├── servstart.service systemd user-юнит (автозапуск в графической сессии)
├── install.sh        деплой (полностью user-scope, sudo НЕ нужен)
├── tests/test_llm.py юнит-тесты логики (19 шт.)
├── PROD-PLAN.md      продакшн-план
└── README.md         этот файл
```

## Что умеет

- **Автопоиск при старте**: бинарники бэкендов (PATH + известные пути) и модели
  `*.gguf` по корням (`/mnt/models`, `~/models`, каталоги Ollama).
- **Info-файл `backends.json`**: справочник бэкендов (llama.cpp, Lucebox, Ollama,
  vLLM, LM Studio, KoboldCpp, llamafile, MLC-LLM, SGLang), составленный по данным
  сети 2026 г. Служит для сопоставления найденного с возможностями.
- **Точное сопоставление** модель ↔ бэкенд по `general.architecture` из заголовка
  GGUF (читается без загрузки тензоров). На этой машине:
  - `qwen4exp` → **llama.cpp** (HIP);
  - `deepseek4` / `deepseek4-dflash-draft` → **Lucebox** (ROCmFPX, llama.cpp не читает).
- **Каскадное меню** в трее: бэкенд → модели (только те, которые бэкенд может
  запустить). Пока модель работает/грузится/останавливается — пункты выбора
  заблокированы (галочка «✓» у запущенной).
- **Живой статус**: имя модели, адрес эндпоинта (`http://host:port/v1`, OpenAI),
  секундомер загрузки/останова («запускаю … N с» / «останавливаю … N с»), память
  **RAM (UMA) total/used**.
- **«Стартовая настройка»**: окно справа вверху, настройки запуска каждого бэкенда
  (порт, контекст, потоки, KV-кэш, слои на GPU, flash attention, MTP, mmproj и т.д.)
  с аннотациями «что это» / «для чего». По **ОК** конфиг сохраняется
  (`~/.config/servstart/config.json`) и передаётся бэкенду **аргументами**.
- **Ошибки запуска**: сбой показывается диалогом с причиной и хвостом лога.
- **«Остановка сервиса»**: останавливает и выгружает все модели (и загружающиеся);
  апплет остаётся в трее (серая иконка). **«Выход»** — останавливает модели и
  завершает апплет.
- **Окна как всплывающие**: при выборе пункта остальные окна закрываются, выбранное
  поднимается наверх; клик вне окна (или по иконке трея) его убирает; изменения в
  настройках применяются только по «ОК». «Готовность» — обычное окно без иконки.
- **Логи — живой поток**: при открытии показывается текущий сеанс (с последнего
  маркера запуска), дальше — только новые строки инкрементально; каждая строка
  получает `[HH:MM:SS]`; новое снизу, автопрокрутка; «в терминале (tail -f)» и
  «показать файл».
- **Иконка-светофор**: серый — ничего не запущено, зелёный — работает,
  красный — сбой. Hint — имя модели/статус через `title`.

## Среда разработки (подобрана под этот хост)

- **Python 3 + PyGObject (GTK3) + AyatanaAppIndicator3** — зависимости стоят:
  `python3-gi`, `gir1.2-gtk-3.0`, `gir1.2-ayatanaappindicator3-0.1`.
- **Интерпретатор строго `/usr/bin/python3`** — только в нём есть `gi`
  (Hermes/venv-питоны в PATH его не видят). Зашито в systemd-юнит.
- **Логика отделена от GUI**: `llm.py` без GTK покрыт юнит-тестами (stdlib
  `unittest`, работает и под `pytest`).
- **systemd user-юнит** `graphical-session.target` — автозапуск при входе.
- **XWayland** (`GDK_BACKEND=x11`) для позиционирования окна справа вверху;
  `GDK_SCALE` не задаётся (иначе двойное масштабирование на fractional-scaling).

## Установка

```sh
cd /mnt/models/servstart
chmod +x install.sh
./install.sh
```

Всё user-scope, `sudo` не нужен: файлы → `~/.local/lib/servstart/`, лаунчер →
`~/.local/bin/servstart` (symlink), юнит → `~/.config/systemd/user/servstart.service`,
затем `enable --now`.

Проверка после установки:

```sh
systemctl --user is-enabled servstart.service   # enabled
systemctl --user is-active  servstart.service   # active
journalctl --user -u servstart -f               # логи апплета
```

Ручной запуск без systemd: `~/.local/bin/servstart`.

## Тесты

```sh
cd /mnt/models/servstart
/usr/bin/python3 -m unittest discover -s tests -v
```

## Управление сервисом

```sh
systemctl --user restart servstart
systemctl --user stop     servstart
```

Удаление:

```sh
systemctl --user disable --now servstart.service
rm -rf ~/.local/lib/servstart ~/.local/bin/servstart ~/.config/systemd/user/servstart.service
systemctl --user daemon-reload
```

## Как это работает (архитектура поведения)

- **Запуск** — в фоновом потоке: preflight (бинарник, модель, размер, порт) →
  `setsid nohup choom -n 1000 -- <бэкенд> <аргументы>` (argv собирается из шаблона
  бэкенда + настроек конфига) → pid в `server.pid` → ожидание `/health` (до 30 мин).
  Статус при этом «запускаю … N с», иконка серая; после готовности — зелёная +
  эндпоинт.
- **Остановка** — по pid из `server.pid`, а если pid-файл утерян — поиск pid по
  слушающему порту (`ss -ltnp`). `SIGTERM` → `SIGKILL`; pid-файл удаляется только
  после фактической смерти процесса. Если процесс в D-состоянии (uninterruptible
  IO при загрузке 90+ GiB), SIGKILL добивается циклически до выхода из IO.
- **Память** — единая картина unified-памяти: `RAM (UMA) total/used` из
  `/proc/meminfo`.
- **Логи** — инкрементальное чтение по offset: при открытии показывается сеанс с
  последнего маркера запуска, дальше только новые строки с `[HH:MM:SS]`; окно
  автопрокручивается вниз. События servstart (запуск/остановка/сбой) пишутся в тот
  же `server.log` с полным timestamp.

## Известные ограничения платформы

- **Tooltip при наведении** на трей-иконку в GNOME недоступен: расширение
  `ubuntu-appindicators` не рендерит tooltip у StatusNotifierItem, а API
  `AyatanaAppIndicator3` не экспонирует поле ToolTip. Сделан максимум возможного:
  `title` (на KDE даёт подсказку) + живой статус первой строкой меню.
- Обе модели не помещаются в память одновременно — при запуске второй сервис
  предупреждает и (с подтверждением) останавливает первую.
- **Остановка во время загрузки не мгновенная**: пока модель грузит 90+ GiB,
  процесс в D-состоянии, и ядро откладывает даже SIGKILL до выхода из IO. Сервис
  продолжает добивать процесс (статус «останавливаю … N с»), пока тот не умрёт.

## Замечания по реализации (best practices)

- **Защита от OOM**: запуск через `choom -n 1000 --` + `setsid` + nohup — при
  нехватке памяти ядро убьёт сервер, а не рабочий стол.
- **`KillMode=process`** в systemd-юните: рестарт/остановка апплета не гасят
  запущенные модели (они в cgroup сервиса, и дефолтный control-group убил бы их).
- **Остановка не теряет pid**: pid-файл удаляется только после подтверждённой
  смерти процесса; запасной путь — поиск pid по порту.
- **Атомарная запись конфига** (tmp + `os.replace`), откат на дефолты при битом JSON.
- Иконки генерируются кодом (без бинарных блобов в репозитории).
- argv, собранный сервисом, совпадает с проверенными лаунчерами
  `/mnt/models/run-qwen38-flashnext.sh` и `/mnt/models/run-ds4-flash.sh`.
- Пункты меню моделей — обычный `Gtk.MenuItem` с галочкой в тексте, а не
  `CheckMenuItem`: `set_active()` у CheckMenuItem эмитирует `activate`, что
  вызывало бесконечный цикл запуск/остановка при каждом обновлении статуса.
