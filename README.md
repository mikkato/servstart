# servstart

Трей-сервис управления **локальными LLM-бэкендами и моделями**. После запуска
сам находит в системе доступные бэкенды и модели, сопоставляет их по справочнику
и даёт запускать/останавливать модели из каскадного меню в системном трее.

## Возможности

- **Автопоиск при старте**: бинарники бэкендов (PATH + настраиваемые пути) и
  модели `*.gguf` по корням, заданным в конфигурации.
- **Справочник `backends.json`**: какие бэкенды известны, как их находить, какие
  форматы/архитектуры моделей они умеют запускать. Служит для сопоставления
  найденного с возможностями.
- **Точное сопоставление** модель ↔ бэкенд по `general.architecture` из заголовка
  GGUF (читается без загрузки тензоров). Бэкенд, который не умеет конкретную
  архитектуру, в своём каскаде её не покажет.
- **Каскадное меню** в трее: бэкенд → модели (только те, что бэкенд может
  запустить). Пока модель работает/грузится/останавливается — пункты выбора
  заблокированы (галочка «✓» у запущенной).
- **Живой статус**: имя модели, адрес эндпоинта (`http://host:port/v1`, OpenAI),
  секундомер загрузки/останова, память **RAM (UMA) total/used**.
- **«Стартовая настройка»**: окно справа вверху, настройки запуска каждого бэкенда
  (порт, контекст, потоки, KV-кэш, слои на GPU, flash attention, спец.-декодеры и
  т.д.) с аннотациями «что это» / «для чего». По **ОК** конфиг сохраняется
  (`~/.config/servstart/config.json`) и передаётся бэкенду **аргументами**.
- **Ошибки запуска**: сбой показывается диалогом с причиной и хвостом лога.
- **«Остановка сервиса»**: останавливает и выгружает все модели (и загружающиеся);
  апплет остаётся в трее. **«Выход»** — останавливает модели и завершает апплет.
- **Окна как всплывающие**: при выборе пункта остальные окна закрываются, выбранное
  поднимается наверх; клик вне окна его убирает; изменения применяются только по
  «ОК». «Готовность» — обычное окно без иконки.
- **Логи — живой поток**: при открытии показывается текущий сеанс (с последнего
  маркера запуска), дальше — только новые строки; каждая получает `[HH:MM:SS]`;
  новое снизу, автопрокрутка; «в терминале (tail -f)» и «показать файл».
- **Иконка-светофор**: серый — ничего не запущено, зелёный — работает, красный —
  сбой. Hint — имя модели/статус через `title`.

## Структура

```
servstart/
├── servstart.py      главный апплет (GTK3 + AyatanaAppIndicator3) — трей, меню, окна
├── llm.py            вся логика без GTK (discovery, сопоставление, конфиг, запуск, метрики)
├── backends.json     справочник бэкендов (для сопоставления и генерации argv)
├── gen_icons.py      генератор иконок-«светофора» (чистый Python, без PIL/cairo)
├── icons/            servstart-gray/green/red.png (генерируются gen_icons.py)
├── servstart.service systemd user-юнит (автозапуск в графической сессии)
├── install.sh        деплой (полностью user-scope, sudo НЕ нужен)

├── PROD-PLAN.md      продакшн-план
└── README.md         этот файл
```

## Требования

- Linux с графической сессией (GNOME/KDE) и `systemd --user`.
- Системный Python 3 с PyGObject и GTK3. На Debian/Ubuntu:

  ```sh
  sudo apt-get install -y python3-gi gir1.2-gtk-3.0 gir1.2-ayatanaappindicator3-0.1
  ```

- Для трей-иконки в GNOME — включённое расширение `ubuntu-appindicators`
  (StatusNotifierWatcher на сессионной шине D-Bus).
- На диске — бинарники бэкендов и файлы моделей (`.gguf`), которые они умеют
  запускать.

## Установка

```sh
tar xzf servstart-deploy.tar.gz -C /tmp/servstart && cd /tmp/servstart
chmod +x install.sh
./install.sh
```

Всё user-scope, `sudo` не нужен: файлы → `~/.local/lib/servstart/`, лаунчер →
`~/.local/bin/servstart` (symlink), юнит → `~/.config/systemd/user/servstart.service`,
затем `enable --now` (автозапуск при входе в графическую сессию).

Проверка после установки:

```sh
systemctl --user is-enabled servstart.service   # enabled
systemctl --user is-active  servstart.service   # active
journalctl --user -u servstart -f               # логи апплета
```

Ручной запуск без systemd: `~/.local/bin/servstart`.

## Настройка под свои бэкенды и модели

Всё, что нужно подстроить под конкретную машину, живёт в `backends.json` и в
конфиге, создаваемом через окно «Стартовая настройка».

`backends.json` — записи бэкендов. Ключевые поля:

```jsonc
{
  "id": "example",                 // уникальный id
  "name": "Example engine",
  "binaries": ["example-server"],  // имена исполняемых файлов
  "search_paths": ["~/engine/bin"],// где искать бинарники (кроме PATH)
  "formats": ["gguf"],             // формат моделей
  "arch": ["myarch"],              // какие GGUF-архитектуры умеет (или exclude_arch)
  "port_default": 8080,            // порт по умолчанию
  "health": "/health",             // эндпоинт проверки готовности
  "argv_template": ["{binary}", "-m", "{model}", "--port", "{port}", "…"], // шаблон командной строки
  "settings": [ /* настройки, доступные пользователю, с аннотациями what/why */ ]
}
```

Модели находятся автоматически по корням, заданным в `servstart.py`
(`llm.find_models([...])`). Сопоставление «какая модель какому бэкенду» — по
`general.architecture` из GGUF-заголовка и полям `arch`/`exclude_arch` бэкенда.

Пользовательские значения настроек (порт, контекст, потоки, …) сохраняются в
`~/.config/servstart/config.json` и при запуске подставляются в `argv_template`.

## Управление сервисом

```sh
systemctl --user restart servstart
systemctl --user stop     servstart
```

Удаление:

```sh
systemctl --user disable --now servstart.service
rm -rf ~/.local/lib/servstart ~/.local/bin/servstart ~/.config/systemd/user/servstart.service
systemctl --user daemon-reload
```

## Как это работает (архитектура поведения)

- **Запуск** — в фоновом потоке: preflight (бинарник, модель, размер, порт) →
  `setsid nohup choom -n 1000 -- <бэкенд> <аргументы>` (argv из шаблона + настроек)
  → pid в `server.pid` → ожидание `/health` (с большим таймаутом на загрузку).
  Статус при этом «запускаю … N с»; после готовности — зелёная иконка + эндпоинт.
- **Остановка** — по pid из `server.pid`, а если pid-файл утерян — поиск pid по
  слушающему порту (`ss -ltnp`). `SIGTERM` → `SIGKILL`; pid-файл удаляется только
  после фактической смерти процесса. Процесс в D-состоянии (uninterruptible IO
  при загрузке большой модели) добивается SIGKILL циклически до выхода из IO.
- **Память** — единая картина unified-памяти: `RAM (UMA) total/used` из
  `/proc/meminfo`.
- **Логи** — инкрементальное чтение по offset: при открытии показывается сеанс с
  последнего маркера запуска, дальше только новые строки с `[HH:MM:SS]`; окно
  автопрокручивается вниз. События servstart (запуск/остановка/сбой) пишутся в тот
  же `server.log` с полным timestamp.

## Известные ограничения

- **Tooltip при наведении** на трей-иконку в GNOME недоступен: расширение
  `ubuntu-appindicators` не рендерит tooltip у StatusNotifierItem, а API
  `AyatanaAppIndicator3` не экспонирует поле ToolTip. Используется `title`
  (подсказка на KDE) + живой статус первой строкой меню.
- Модели, которые не помещаются в память одновременно, при запуске второй сервис
  предупреждает и (с подтверждением) останавливает первую.
- **Остановка во время загрузки не мгновенная**: пока идёт загрузка большой модели,
  процесс в D-состоянии, и ядро откладывает даже SIGKILL до выхода из IO. Сервис
  продолжает добивать процесс (статус «останавливаю … N с»).

## Замечания по реализации (best practices)

- **Защита от OOM**: запуск через `choom -n 1000 --` + `setsid` + nohup — при
  нехватке памяти ядро убьёт сервер, а не рабочий стол.
- **`KillMode=process`** в systemd-юните: рестарт/остановка апплета не гасят
  запущенные модели (иначе дефолтный control-group убил бы их вместе с апплетом).
- **Остановка не теряет pid**: pid-файл удаляется только после подтверждённой
  смерти процесса; запасной путь — поиск pid по порту.
- **Атомарная запись конфига** (tmp + `os.replace`), откат на дефолты при битом JSON.
- Иконки генерируются кодом (без бинарных блобов в репозитории).
- Пункты меню моделей — обычный `Gtk.MenuItem` с галочкой в тексте, а не
  `CheckMenuItem`: `set_active()` у CheckMenuItem эмитирует `activate`, что
  вызывало бесконечный цикл запуск/остановка при каждом обновлении статуса.
